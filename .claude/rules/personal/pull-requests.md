# Pull requests

## Merging

Assume a squash merge unless the repo says otherwise. The title and the
description become the commit message, so write them for that.

## Title

- Start with a capitalized imperative verb: `Fix`, `Add`, `Refactor`. Do not
  write `Fixes` or `Adding`. Repo conventions (e.g. semantic commits) take
  precedence over this rule.
- Write one sentence. Use two words minimum and 70 characters maximum.
- Do not add trailing punctuation.

## Description

The diff shows what changed. The description explains why.

- Summarize in one to three sentences. Do not paraphrase the diff line by
  line.
- State the motivation: the feature, the bug, the incident, the user request,
  or the constraint. Without it, a reviewer cannot weigh the change against
  its churn, and a future maintainer does not know what is safe to change.
- Link the evidence: an error tracker issue, a dashboard panel, an incident
  thread, a ticket, a design document, a prior PR. A linked graph is better
  than a sentence about the graph.
- Call out a non-obvious choice: a rejected alternative, a deferred
  follow-up, the expected rollout behavior, a known risk.
- Omit a section that has nothing to say. Empty boilerplate hides the parts
  that matter.
- Do not add an attribution footer or a "generated by" line.
- Do not pad a short change into a long description. A one-line fix needs one
  or two sentences.

## Match the repo's PR template

Look for a template every time you write a PR body, both for a draft in chat
and for a PR you open directly:

```
find <repo-root> -maxdepth 3 -iname 'pull_request_template*'
```

GitHub reads the template from the repo root, from `.github/`, or from
`docs/`. It can be one `.md` file or a directory of templates. If it is a
directory, pick the template that matches the type of the change.

When a template exists, build the body around its sections. Do not invent
your own.

- Reuse the headings of the template, for example `## Description`,
  `## Verification steps`, `## Pre-merge steps`.
- Keep the checklists and the required steps. Uncheck a step that is not
  done. Do not delete it. These steps carry the norms of the repo.
- Drop the HTML comment hints (`<!--- ... --->`). They are author guidance,
  not content for a reviewer.
- Add a new section only when the template has no place for what you need,
  for example a "History" section for a revert of a revert. Put it after the
  main section of the template, so the primary content stays first.

## Checkboxes

An unchecked `- [ ]` is a merge blocker. It promises that the step happens
before the merge.

- Use a checkbox only for a manual pre-merge step that still needs a human.
- Do the steps you can do yourself, for example tests, lint, and build. Then
  check them off.
- Write an item that cannot finish before the merge as a plain bullet, never
  as a checkbox. Examples: post-deploy monitoring, a follow-up deploy, a
  CI-enforced check. An unchecked box blocks the merge and a checked box is
  false.
- Write a post-merge item in the future tense: "After the deploy, watch ...".
